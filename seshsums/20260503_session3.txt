     David, Jeff, and Roussel debated three topics:

     a. Equivalence understanding (David)
        David raised the children's-algebra-error literature: kids given
        "3+4+1 = 3+_" often answer 8 or 11 (treating = as "compute left side")
        rather than 5 (treating = as a relation). He suggests the model may
        exhibit the same bug if trained without relational-equals examples.
        This is now queued as TN-003 (see below), with the blank char changed
        from `_` to `?` since `_` is now used as the separator.

     b. Research scope clarification (Jeff)
        Jeff clarified what the project is and is not:
        - NOT modeling real algebra development or human-plausible sequences.
        - "Developmental sequence" = ordered curriculum (easy->hard) only.
        - Goal: observe whether training order affects abstraction formation
          in a formal system, and find generalizations in the GPT stack.
        - Training from scratch; no pretrained NLP models (confound: can't
          attribute generalization to curriculum if prior knowledge present).
        - Neutral symbolic tags (e.g. `a`, `b`) labeling rule applications
          are of interest: do they accelerate abstraction formation even though
          the tags carry no semantic content to the model?

     c. Pre-training vs. from-scratch (Roussel)
        Roussel proposed two things, which are actually distinct:
          1. Use NLP-pretrained LLMs (Deepseek, Qwen) as a starting point.
             Jeff ruled this out: prior knowledge is an uncontrolled confound.
          2. Pre-train within the formal system on broad algebraic instances,
             then fine-tune on the specific task.
             Jeff did not explicitly address this; it is NOT ruled out and
             remains open as a future experiment.

  3. Separator change: `->` replaced with `_`  (TN-005, now DONE)
     The `->` separator was two characters; `-` also appears in expressions and
     targets, making it visually ambiguous. `>` appeared only in `->`, so it was
     technically unambiguous, but still inelegant.
     Replacement: single char `_`, which never appears in expressions or targets.
     Changes made:
       data_gen.py:
         - VOCAB: replaced `>` with `_`  (still 15 chars; same VOCAB_SIZE)
         - Docstring: updated format description
         - make_pair(): `expr_to_str(expr) + '->' + rewrite(expr)`
                     -> `expr_to_str(expr) + '_' + rewrite(expr)`
         - Smoke test split: `s.split('->')[1]` -> `s.split('_')[1]`
       train.py:
         - SEP_ID: `_C2I['>']` -> `_C2I['_']`
         - AlgebraDataset docstring example updated
         - collect_correct_deep: `raw.split('->')` -> `raw.split('_', 1)`
                                  `encode(src + '->')` -> `encode(src + '_')`
         - train() sample predictions: same two changes as above
         - Module docstring updated
     Note: all datasets generated before this change are incompatible.
     Note: TN-003 originally used `_` as the blank char in relational-equals
     training examples. That design must now use a different char (e.g. `?`).

  6. LR reset discussion
     Raised: should the LR schedule reset at each curriculum stage transition?
     Tradeoff:
       Loss: theoretically, a high LR after a stage transition could destabilize
       representations learned in prior stages. In practice this risk is low
       because later stages contain the same shallow sub-expressions, so depth-2
       representations are reinforced, not overwritten.
       Gain: avoids training Stage 4 under a near-dead LR. The model sees
       genuinely novel hard examples for the first time and needs real gradient
       signal to make progress.
     Recommended design: per-stage cosine schedule with a short warmup, resetting
     at each stage transition. Requires deciding per-stage budget (explicitly or
     tied to stage duration). Not implemented yet; deferred to next session.
